Для Dev Containers используются обычные Docker-образы. Никакой «магии» внутри них нет — это стандартные образы из Docker Hub. Любой Docker-образ, в котором есть Linux и Bash, технически может стать средой разработки.

Однако, чтобы вам не пришлось вручную дописывать установку базовых утилит (вроде `git`, `curl` или `openssh`), сообщество создало две категории образов.

Вот как выбрать то, что нужно именно вам:

### 1. Официальные универсальные образы (Рекомендуемый путь)

Microsoft и сообщество поддерживают огромный репозиторий готовых, оптимизированных образов для разработки. Они называются **Devcontainer Images**. В них уже «из коробки» настроены права пользователя (не root, а безопасный `vscode` или `node`), установлены Git, zsh/bash, правильные локали и таймзоны.

Их легко узнать по префиксу `[mcr.microsoft.com/devcontainers/](https://mcr.microsoft.com/devcontainers/)`.

**Как понять, какой нужен:**

- **Вам нужен просто Linux для экспериментов?**
    
    👉 `[mcr.microsoft.com/devcontainers/base:ubuntu](https://mcr.microsoft.com/devcontainers/base:ubuntu)` или `.../base:debian`
    
- **Вы пишете на конкретном языке?**
    
    Выбирайте образ, заточенный под ваш стек. В него уже предустановлен рантайм нужной версии:
    
    - Для Node.js: `[mcr.microsoft.com/devcontainers/javascript-node:20](https://mcr.microsoft.com/devcontainers/javascript-node:20)`
        
    - Для Python: `[mcr.microsoft.com/devcontainers/python:3.11](https://mcr.microsoft.com/devcontainers/python:3.11)`
        
    - Для Go: `[mcr.microsoft.com/devcontainers/go:1-21](https://mcr.microsoft.com/devcontainers/go:1-21)`
        

Полный список этих образов всегда можно найти на GitHub в репозитории `devcontainers/images`.

### 2. Стандартные Docker-образы (Для продакшена)

Если вы хотите, чтобы среда разработки была **на 100% идентична тому, что будет крутиться на сервере в продакшене**, вы можете указать абсолютно любой официальный образ с Docker Hub.

- Например, `image: "postgres:16"` или `image: "python:3.11-slim"`.
    

> ⚠️ **Минус этого подхода:** В «чистых» продакшен-образах часто нет даже `git` или `unzip`. Из-за этого Zed или VS Code при первом запуске могут споткнуться, пытаясь поставить туда свои серверные компоненты для работы автодополнения.

### 3. Кастомный Dockerfile (Профессиональный путь)

Если вашему проекту нужен не просто язык программирования, а специфический набор системных библиотек (например, утилиты для работы с графикой `ffmpeg`, базы данных, специфические CLI-инструменты), вы вместо готового `image` подключаете свой `Dockerfile`.

В `devcontainer.json` это пишется так:

JSON

```
{
  "name": "Custom Python + Fmpeg Env",
  "build": {
    "dockerfile": "Dockerfile" // Ссылка на файл рядом
  }
}
```

А в самом `Dockerfile` вы берете за основу базовый dev-образ и доставляете туда всё, что нужно:

Dockerfile

```
FROM mcr.microsoft.com/devcontainers/python:3.11

# Устанавливаем дополнительные системные пакеты
RUN apt-get update && apt-get install -y ffmpeg htop
```

### Шпаргалка для выбора:

1. Если проект стандартный (Node/Python/Go) — берите **официальный образ от Microsoft** (`[mcr.microsoft.com/devcontainers/](https://mcr.microsoft.com/devcontainers/)...`). Это сэкономит кучу времени.
    
2. Если нужны кастомные утилиты ОС — создавайте связку `devcontainer.json` + `Dockerfile`.
    
3. Если нужно поднять рядом базу данных (например, Redis или PostgreSQL) — в будущем вы подключите `docker-compose.yml`, но об этом позже.

# FEATURES

Да, давай разберем этот момент, потому что здесь кроется самое красивое архитектурное решение во всей этой технологии.

Когда мы говорили про `base:ubuntu` + **Features**, мы обсуждали подход **«Конструктор»**. Когда мы говорили про `javascript-node:20`, мы обсуждали подход **«Готовый монолит»**.

Разница между ними — в гибкости и в том, кто управляет составом инструментов.

### Подход 1: Чистая Ubuntu + Features (Конструктор)

Ты берешь абсолютно «голую» операционную систему и собираешь свой стек по кирпичикам прямо в файле `devcontainer.json`.

JSON

```
{
  "image": "mcr.microsoft.com/devcontainers/base:ubuntu",
  "features": {
    "ghcr.io/devcontainers/features/node:2": { "version": "20" },
    "ghcr.io/devcontainers/features/python:1": { "version": "3.11" },
    "ghcr.io/devcontainers/features/docker-in-docker:4": {}
  }
}
```

- **Как это работает:** Спецификация Dev Containers сама знает, как залезть внутрь Ubuntu и правильно установить туда Node.js, Python или Docker. Она скачивает проверенные скрипты автоматизации (Features) и накатывает их поверх чистой ОС при сборке.
    
- **Плюсы:**
    
    - **Максимальная гибкость.** Тебе нужен Node.js 20 и Python 3.11 в одном месте? Просто допиши две строчки.
        
    - **Легко обновлять.** Захотел обновить Node.js до 22 версии — просто поменял цифру в конфиге.
        
- **Минусы:** Сборка контейнера в первый раз занимает чуть больше времени, потому что скрипты физически скачивают и устанавливают пакеты внутрь ОС.
    

### Подход 2: Готовый образ (Монолит)

Ты берешь образ, который инженеры Microsoft _уже_ собрали заранее. Они взяли ту же Ubuntu, установили туда Node.js, настроили все кэши и запаковали это в один готовый файл-слепок.

JSON

```
{
  "image": "mcr.microsoft.com/devcontainers/javascript-node:20"
}
```

- **Как это работает:** Docker просто скачивает готовый тяжелый слепок, где Node.js уже вшит в саму систему.
    
- **Плюсы:** **Молниеносный старт.** Контейнер запускается за секунды, потому что внутри ничего не нужно доустанавливать. Всё уже готово.
    
- **Минусы:** Если тебе посреди проекта внезапно понадобится Python или AWS CLI, тебе придется либо писать кастомный `Dockerfile`, либо... всё равно подключать механизм **Features** поверх этого образа.
    

### Что и когда выбирать (Middle-практика)

1. Если твой проект **моно-язычный** (чистый фронтенд на React/Next.js или чистый бэкенд на Python) — бери **Готовый образ** (`javascript-node` или `python`). Это быстрее и проще.
    
2. Если у тебя **сложный стек** (например, Node.js + Python для ИИ-скриптов + PostgreSQL + Docker внутри контейнера) — бери **Base Ubuntu и собирай через Features**. Это избавит тебя от необходимости писать огромные и запутанные `Dockerfile` с кучей команд `apt-get install`.
    

> **И главное:** Features можно накатывать абсолютно на _любой_ образ. Ты можешь взять готовый `javascript-node:20` и через блок `features` докинуть туда только Python. В реальной работе чаще всего используют именно такой гибридный подход.
